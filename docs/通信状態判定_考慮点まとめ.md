# EtherNet/IP通信状態ツリー表示 設計における考慮点

「診断対象ユニット」以下をツリー表示し、各ノードの通信状態(正常/異常)をアイコン表示する設計にあたり、単純な2値判定では不十分な点を整理したものです。

対象ツリー構造:
```
診断対象ユニット
　アダプタ
　　コネクション
　タグ
　スキャナ
　　ターゲットユニット
　　　コネクション
```

---

## 1. 通信の成立段階が複数あることの考慮

EtherNet/IPは「物理疎通 → TCP接続 → EtherNet/IPセッション → CIPコネクション」という複数段階を経て初めて正常となる。どの段階で止まっているかを判定できる設計が必要。

| 段階 | 内容 | ここで止まる場合の見え方 |
|---|---|---|
| ① 物理/IP到達性 | ping等 | 疎通不可 |
| ② TCPセッション確立 | ポート44818への接続 | TCP接続不可(**通信サービス未起動**を含む) |
| ③ EtherNet/IPセッション登録 | RegisterSessionコマンド | TCPは繋がるがセッション登録が拒否/無応答 |
| ④ CIPコネクション確立 | Forward Open | Extended Statusでエラー種別判明 |
| ⑤ データ交換継続 | I/Oデータの周期更新 | 確立後にタイムアウト/途絶 |

**③ EtherNet/IPセッション登録** は見落としやすい段階。TCP自体は繋がるが、ターゲットの同時セッション数上限超過などでRegisterSessionが拒否される場合があり、これは「TCP疎通OK・CIPエラーコードなし」という中間状態になる。

> **重要:** CIPのExtended Statusは④の段階で初めて取得できる情報であり、①〜③で止まっている場合(通信サービス未起動、疎通不可等)には一切現れない。エラーコードのみで判定すると、これらのケースを検出できない。

---

## 2. 「確立できるか」と「確立後も維持できるか」は別問題

当初の議題は「コネクションが確立できないパターン」だったが、実運用では**一度確立した後に切断される**ケースの診断も重要。

- RPI周期でのデータ未着が一定回数(Connection Timeout Multiplier)続き、タイムアウト切断
- ネットワーク輻輳による間欠的なパケットロス
- ターゲット側の負荷変動による応答遅延

「異常」アイコンを「確立失敗」と「確立後の切断」で分けて表示するかは、設計上の重要な分岐点。

---

## 3. データは届いているが「有効」ではない状態(Run/Idle)

コネクションが正常に確立されていても、生成側(スキャナ/ターゲット)が **Idleモード**(プログラム停止中など)の場合、データヘッダのRun/Idleビットが「Idle」になる。

- 通信としては正常だが、データとしては無効
- ツリー表示上、これを「正常」「警告」「異常」のどれとして扱うかを要検討

---

## 4. 診断ツール自身の疎通経路

「診断対象ユニット」を選択して状態表示する際、**診断ツール(本アプリ)自体が対象ユニットと通信できるか**も独立した前提条件。

- 対象ユニット同士(スキャナ↔ターゲット)は正常でも、診断ツールが情報取得のためにアクセスするパス(ユニットの管理用ポート等)が別に途絶している可能性がある
- この場合、「対象ユニットが異常」なのか「診断ツールが情報を取得できないだけ」なのかを区別して表示する必要がある

---

## 5. 複数配下ノードの集約ステータス

「スキャナ」配下に複数の「ターゲットユニット」、「アダプタ」配下に複数の「コネクション」がある場合、親ノードのアイコンをどう決めるかのルールが必要。

| 配下の状態 | 親ノードの表示(案) |
|---|---|
| 全て正常 | 正常 |
| 一部異常 | 「一部異常」の中間アイコン |
| 全て異常 | 異常 |
| 配下が0件(未設定) | 「未使用/未設定」 |

---

## 6. タグ(Explicit Message)とコネクション(Implicit/I-O)は判定軸が別

ツリー上は同列に見えるが、判定に使う情報源が異なる。

- 「コネクション」:Forward Openの成否、RPI周期でのデータ更新有無
- 「タグ」:個々のCIPサービス要求(Get/Set Attribute等)ごとの応答有無・エラー

**コネクションが全て正常でも、タグだけ個別に異常になり得る(逆も同様)。** 同じ判定ロジックを流用しようとすると齟齬が出るため、別ロジックとして設計する必要がある。

---

## 7. 状態区分の再定義(2値では不足)

正常/異常の2値ではなく、最低限以下の区分が必要になると考えられる。

| 状態 | 説明 |
|---|---|
| 正常 | 通信確立・データ交換継続中 |
| 未設定/未使用 | そもそも当該機能を使っていない(タグ未使用、アダプタ機能OFF等) |
| 確立前(初期化中) | 起動直後などでこれから接続を試みる状態 |
| 異常(確立不可) | 一度も確立できていない |
| 異常(切断/タイムアウト) | 確立していたが通信断になった |
| 警告(不安定) | 間欠的なタイムアウト・再接続を繰り返している |

---

## 実装への示唆

原因リスト(何が異常か)を先に作り込むよりも、まず以下を先に定義しておくことを推奨する。

1. **ツリー各ノードが、どの情報源(TCP到達性/セッション有無/CIPステータス/データ更新タイムスタンプ/Run-Idleビット等)を使って状態判定するか**を先にマッピングする
2. 判定ロジックを次の2段階に分ける
   - 第1段階:TCP/UDPレベルでの到達性判定(通信サービス未起動・疎通不可を検出)
   - 第2段階:到達できていた場合のみ、CIPレベルのExtended Statusで詳細原因を判定
3. 親ノードの集約表示ルール(全滅/一部異常/全正常/未使用)を先に決める
4. 「コネクション」と「タグ」は別判定ロジックとして扱う

この順序で設計することで、原因リストの追加・変更があっても表示ロジック自体を作り直す必要がなくなる。
